# 料理・買い物システム

## 既存構造と変更点

v0.1はClassic scriptの `globalThis.Life` に定義を登録し、ActionSelector → EventResolver → WorldStateManager → MemoryLoggerの順で状態と日記を更新していた。保存処理はsimulation.js内のLife.Storageにあった。

v0.2は生活のスケジュール・不在圧縮・会話の入口を維持し、料理の純粋関数をcooking.js、保存をstorage.js、プリセットをpresets/に分離する。index.htmlの読み込み順はレシピ→食材→おやつ→共通データ→料理→イベント→シミュレーション→保存→UI。外部通信・ビルド・ES Modulesは不要。

## データの追加

先に `presets/recipes.js` に料理を定義し、必要な共通食材を `presets/ingredients.js` に登録する。おやつは `presets/snacks.js` に登録する。IDは保存履歴に使うため変更・再利用しない。

食材の属性は `name, type, taste[], texture[], methods[], substitutes[], emoji`。レシピは `name, difficulty (0〜1), result, slots[]`。各slotは `id, role, quantity (正整数), requires: {taste[], texture[], methods[]}` を持つ。数量はゲーム内の抽象単位で、調味料は暗黙に含む。

`Life.validateCatalog()` が参照と属性を検証し、レシピの材料枠から利用回数を抽出する。`Life.commonIngredients()` が利用回数順の共通食材を返す。おやつの選択肢と初期在庫も定義から生成する。レシピ・食材を追加するためにエンジンへIDの分岐を追加する必要はない。

保存には既知のカタログIDも保持する。次回読込で新定義の食材を在庫0、新レシピを利用可能として追加する。既知食材の数量欠落は破損として拒否する。

## 献立・代用・結果

- `menuPreference` の初期値は在庫0.7・食べたい料理0.3。在庫方式は正規材料の充足率、食べたい料理方式は成功失敗経験を重みにする。直近4料理の同種繰り返しは0.25倍ずつ抑制。
- 不足時の選択重みは買い物3、代用4×適合度×学習補正、別料理2。全材料を揃えられる選択肢だけを採用。買い物待ちの献立を保持する。
- 代用は役割35%・味25%・食感20%・調理適性20%。属性の要求タグに対する一致率を使い、要求のない項目は除いて正規化する。正規食材は1。0.25未満の候補は除外する。
- 材料枠ごとに私的在庫へ仮予約し、一つの在庫を二重に使わない。不足数量は材料枠間で累積する。
- 買い物は不足量を満たし、購入対象を最低4単位まで補充する。常備品補充は複数レシピに出る食材から最大4種を選ぶ。
- 評価値は `0.8×平均適合度 + 0.2×min(経験/30,1) − 0.2×難易度 + 乱数[-0.05,0.05)`。0.70以上はsuccess、0.45以上はunusual、それ以外はfailure。
- どの結果でも実際の使用量を消費し、経験を1加算する。失敗料理は食事の会話に含めない。
- 学習キーは `[レシピID, 材料枠番号, 代用品ID]` のJSON文字列。試行・成功・変わった料理・不適合失敗・その他の失敗を集計する。不適合失敗は代用適合度0.7未満の場合。補正は `1/(1+max(0,不適合失敗−成功×0.5)×0.7)` で、候補順位と代用の選択確率に反映する。

これは架空世界の調理演出であり、現実の料理の安全性、食べられるかどうか、加熱条件などの判断には使用できない。

## 状態・イベント・保存

`WorldStateManager.process(event)` が在庫差分・経験・学習・乱数・イベントIDを私的な下書きへ適用し、検証後に一括確定する。確定履歴を再帰的にfreezeして共有することで長期のコピー負荷を抑える。`state` は独立コピー、`snapshot` は読み取り専用ビュー。

調理イベントには `menu, shortage, recipeId, ingredientsUsed, substitutions, evaluation, result, effects` を保存する。購入イベントには `itemsBought, requestedQuantities, recipeId, reason` を記録する。消費は調理イベントに含め、二重計上する独立消費イベントは生成しない。日記と会話は確定イベントの文章を利用し、記録していない出来事を作らない。

`Life.StateCodec.encode/decode/migrate` はブラウザー非依存。`Life.Storage.load/save/reset(storage, ...)` はgetItem/setItemだけを使う同期アダプター。Sites等で非同期保存を導入する場合はアダプターとUIの保存呼出部分を変更し、生活エンジンとCodecを再利用できる。

v1は元JSONの検証後にコピー上で移行する。過去ログと日記、在庫、経験、乱数、時刻を保持し、新機能だけ初期化する。旧集計は再解釈せず、unusualは0から新規計上。初回保存前に元JSONをバックアップし、失敗時は主キーを更新しない。明示リセットでも元JSONをbackup-resetキーに保管する。

旧イベントの在庫スナップショットは旧10品目のまま保存される。移行後のイベントは40品目となるため、移行前後をまたぐ外部監査では新規品目の初期在庫0を補完する。

ログ上限1,800件・日記180日・圧縮区間32件は維持する。通常精度の高速検証は日単位でadvanceを呼び出し、外部テスト側で全確定イベントを収集する。不在圧縮は代表イベントによる近似であり、通常精度の結果と一致することは要求しない。
