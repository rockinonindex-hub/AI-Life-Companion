# AI Life Companion v0.2 — ふみの暮らし

小さな部屋でフミが読書・料理・趣味を楽しむ、ブラウザーだけで動く生活シミュレーションです。LLM・外部API・外部ライブラリ・通信処理は使いません。

## 起動

1. ZIPを右クリックし「すべて展開」します。
2. 展開した `AI-Life-Companion` 内の **index.html** を、WindowsのEdgeまたはChromeで開きます。
3. インストール・ビルド・サーバー起動は不要です。スマートフォン幅でも表示できます。

部屋を開いている間は30秒ごとに生活時計を確認し、**仮想時間の90分ごと**に生活行動を1件進めます。最初の訪問でも1件実行します。動作をすぐ確かめるには、右上の歯車から「1日進める」「7日進める」を押してください。

## 使い方

- **おやつ**：10種類から選んで渡せます。フミはその場で食べる／棚に保存／料理用に取っておく、のいずれかを選びます。料理用にしたおやつも、属性が合うレシピと条件がそろったときにだけ使います。
- **会話**：「今日何してた？」「昨日何してた？」「何食べた？」「最近何に興味がある？」「日記を見せて」に対応。自由会話は未実装です。会話履歴は画面内のみ、生活の記憶は保存されます。
- **日記**：実ログの重要度・種類から1日1〜3件を選びます。同じ日の新しい出来事に応じて書き直します。参照イベントIDも表示します。
- **開発モード**：状態、最新100件のログ、次の行動時刻での選択重み、時間送り、名前変更、状態JSONの書き出し、初期化。JSON書き出しは確認・保管用で、インポート画面は今回含めていません。

「7日進める」は実時計より先に生活時計を進める検証操作です。その後は「検証用の生活時計」と表示し、現実の時計が追いつくまで逆行させません。再び実時計から始めたい場合は、必要な記録を書き出してから初期化してください。

## ファイルと責務

| ファイル | 役割 |
| --- | --- |
| index.html | 部屋・おやつ・会話・日記・開発画面 |
| style.css | CSSによる家具・キャラクター・レスポンシブ表示 |
| presets/*.js | レシピ20種・通常食材30種・おやつ10種の独立定義 |
| data.js | 定義の検証、初期状態、シード付き乱数 |
| cooking.js | 献立選択、代用評価、調理・買い物イベントの解決 |
| storage.js | 保存アダプター、スキーマ移行、JSON変換 |
| events.js | WorldStateManager、EventResolver、MemoryLogger、整合性検査 |
| simulation.js | ActionSelector、時間経過、独立した会話関数 |
| app.js | UI操作と生活エンジンの接続、保存、定期更新 |
| tests/run-tests.cjs | Node.js標準機能だけで実行する再現性・整合性テスト |
| samples/seven-days.json | 固定シードで実行した7日分の全World State |
| samples/seven-days.md | 同じ実行の全生活ログ・日記・最終在庫・興味の変化 |

Classic scriptと `globalThis.Life` を使い、ES Modulesやfetchに依存せず、ファイルを直接開ける構成です。UIからエンジンを直接書き換えず、すべて `WorldStateManager.process(event)` を通します（新規作成・初期化・保存済み状態の読込を除く）。

**World State → Action Selector → Event Resolver → Memory Logger → World State**

Resolverは状態を書き換えず、食材増減・興味・活動・経験などのeffectsを持つイベントを返します。Managerが私的コピーへ適用し、在庫が非負整数であることなどを検証し、記録と状態を同時に確定します。不正な処理はログ・イベントID・状態のすべてを確定前に破棄します。時計と日記の更新もイベント処理を通しますが、生活ログには載せません。このため生活ログのイベントIDに欠番があります。

## 因果関係の仕組み

- 食材不足 → 買い物メモ → 買い物の重み上昇 → 在庫補充 → 料理可能。
- 調理成功／失敗 → 経験・レシピごとの成績・興味更新 → 次の料理やレシピの選択率が変化。
- 料理本／植物の本など → 分野への興味更新 → 行動・読書や趣味の題材が変化。
- 直近4行動の同種繰り返しを0.42倍ずつ抑制。趣味の題材も直近の履歴から抑制します。夜は睡眠を優先する例外があります。
- 興味は個人ごとの基準値に向かって時間とともに戻り、同じ題材の続行による飽きも加わります。性格は固定です。
- 献立は在庫優先70%・食べたい料理優先30%。食材不足時は買い物・代用・別料理を選びます。代用は役割・味・食感・調理適性を照合し、不適切な代用による失敗を学習します。食材IDに固有の面白イベントはありません。
- 調理結果は成功・変わった料理・失敗の3段階です。適合度と経験を主材料とし、±0.05の乱数を加えます。評価は架空の生活シミュレーション用であり、現実の料理の安全性評価には使えません。
- 調理計画内で食材を仮予約するため、1個の食材を複数の必須枠に二重利用しません。失敗時にも実際の使用量を消費します。調味料はレシピに暗黙に含め、個別在庫としては扱いません。

## 不在期間の扱い

| 期間 | 処理 |
| --- | --- |
| 直近3日以内 | 90分刻みの通常イベント |
| それ以前の約2週間まで | 1日約4件、最大56件の代表イベント |
| それ以前の約8週間まで | 1日約2件、最大64件の代表イベント |
| さらに長い期間 | 全体から最大24件の代表イベントと期間要約 |

代表イベントでも同じResolverで在庫・経験・興味を更新します。最後の3日間は通常処理します。1回の追いつきは最大160行動に制限します。年単位でも全日をループしません。要約に記載する料理の回数等は、生成した代表ログの実数です。

これは省略期間の全行動を厳密に再現する方式ではありません。長期不在では料理経験や在庫なども**代表イベントによる近似状態**です。代表記録を含む日には日記・会話でその旨を表示し、記録していない個々の出来事を補作しません。閉じていた間に実際の情報検索や仕事をしたことにもなりません。

## 保存と記録の上限

v0.1の保存はキーを維持してv2へ移行します。新規食材は在庫0で追加し、基本20レシピを利用可能にします。初回保存の前に旧JSONを `ai-life-companion.v1.backup-v1` に保管します。過去の履歴・日記・成功失敗集計は書き換えません（旧版の「変わった料理」は従来の成功集計に含まれたままです）。バックアップや保存に失敗した場合は元の保存を維持します。

同じブラウザー・プロファイル・ファイルの場所で開くとlocalStorageの状態を継続します。別PC・別ブラウザーとの同期はありません。ファイルURLに対する保存の扱いはブラウザーによって異なるため、別フォルダーへの移動、プライベートモード、閲覧データ削除で継続できなくなる場合があります。保存に失敗したら画面に表示します。壊れた保存データを検出した場合は上書きせず、一時的な部屋を開きます。複数タブの変更を検知したタブは操作を停止し、再読込を案内します。

生活ログは最新1,800件、日記は最新180日、圧縮区間の情報は最新32区間に上限を設けています。日記に選ばれなかった出来事も、生活ログの保存上限内では保持します。上限を超えた古いログの件数は `archivedEvents` に残します。古い日記の参照イベントが既に保存上限から外れている場合もあります。長期の完全保存が必要なら、状態JSONを定期的に書き出してください。

## 検証

通常利用にNode.jsは不要です。開発テストを実行する場合だけNode.jsを使います。日本のWindowsで、このフォルダーをPowerShellで開いて実行します。

```powershell
$env:TZ = 'Asia/Tokyo'
node .\tests\run-tests.cjs
node .\tests\cooking-tests.cjs
node .\tests\simulate.cjs
```

既存19項目と料理・保存の追加14項目を検証します。最初のコマンドは`samples/seven-days.json` と `samples/seven-days.md` を再生成します。サンプルは2026年11月1日0:00から7日間、固定シード20261101、毎日チェックポイントを置いた通常精度の実行です。アプリの「7日進める」は不在時と同じ圧縮経路を使うため、サンプルとイベント数・内容が異なります。時刻帯によって選択率が変わるので、別のタイムゾーンでは結果も変わります。

高速検証は7・30・180日の通常精度／圧縮をそれぞれ2回実行し、全イベントと最終状態が固定シードで一致することを確認します。集計は `samples/simulation-report.json`、検証結果と変更一覧は [検証レポート](docs/verification.md)、設計と追加方法は [料理システム](docs/cooking-system.md) を参照してください。

テスト対象は在庫不足からの買い物、在庫の全履歴再計算、失敗時の消費、二重利用防止、処理失敗時の巻戻し、乱数再現性、興味・成否・繰り返し抑制の影響、属性による代用、日記と会話の出典、保存復元、破損データの保護、おやつの3分岐、興味の減衰、圧縮処理の整合性、100年不在の計算上限、記録サイズ上限です。

ブラウザーでも、おやつ→会話→日記、7日送り、再読み込み後の継続を確認できます。開発モードのWorld Stateとイベントの `inventoryBefore / inventoryAfter / ingredientsUsed / effects / selection` を比べると、状態と後続選択のつながりを追えます。

## 今後の拡張境界

会話は `Life.respond(question, world, at)`、保存は `Life.Storage` に独立させています。将来のLLM会話や保存先変更はここを差し替えられます。生活行動の追加はデータ・Selector・Resolverに追加します。調査や仕事などの外部実行機能は今回含めず、生活エンジンとは別サービスとして設計できます。
